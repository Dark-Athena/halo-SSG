【GaussDB】预警复现：CLD-P-A-202563 执行to_char或to_timestamp函数导致数据库发生coredump

背景

有次收集了某客户所有测试环境GaussDB的ffic日志，发现里面大量的coredump都发生在to_char函数，联想到之前华为有发过相关预警，但是我当时并没有去实验验证，所以这次来尝试复现一下。

【问题描述】
O兼容性数据库使用to_char或to_timestamp函数报错后，修改a_format_dev_version参数（set a_format_dev_version ='';），再次执行to_char或to_timestamp函数导致数据库发生coredump。

【触发因素】
因素一：GaussDB内核版本为：GaussDB Kernel 503.0（包含）~ GaussDB Kernel 505.2.1.SPC0800（不包含）、506.0.0 SPC0100
因素二：GaussDB数据库兼容性为O，集中式、分布式均涉及。。
因素三：设置set a_format_version='10c'，set a_format_dev_version='sx'(sx表示s1、s2、s3、s4、s5、s6，后续举例使用s6)，已经使用17种及以上不同的timestamp时间格式。调用 to_char(timestamp, 'yyyy年mm月dd日')或者to_timestamp('2025年01月01日', 'xxxx年xx月xx日') 等使用带中文时间格式时，出现格式错误的报错，此时设置set a_format_dev_version ='';，再次调用to_char(timestamp, 'yyyy年mm月dd日')或者to_timestamp('2025年01月01日', 'xxxx年xx月xx日')。

--使用17种timestamp时间格式

select to_char(current_date, 'YYYY年MM月DD日'); --发生core

【问题根因】
对于timestamp/timestamptz类型的数据，可以根据format格式输出数据，数据库内部会缓存format格式解析结果，缓存上限是17种format格式。达到缓存上限后，会从缓存中获取一块使用频率最低的缓存继续使用，此时缓存中的解析信息仍然存在，不会清理。当设置a_format_version='10c'和a_format_dev_version='s6'时，如果format格式有中文产生报错，会导致缓存块处于异常状态。此时设置a_format_dev_version=''，再次执行相同带有中文format格式的SQL语句时，会复用到该异常缓存块，使数据库发生coredump。

复现

我当前版本是506.0.0 SPC0100 ，直接使用预警文档里的复现用例，是复现不出来的，仔细看了下，是因为这个版本默认开启了mapping_date_to_datea=on,这个参数相关介绍可以参考我之前写的一篇文章 https://www.darkathena.top/archives/gaussdb-506-date-type-oracle
,简单来说，这个其实就是把执行sql中的date类型语义映射成datea类型。而预警说的是timestamp类型，所以预警里的用例需要关闭这个参数才能复现，或者说，要更老的版本才可以复现。开了mapping_date_to_datea后，不接受中文格式，直接就拦住了，进不去有问题的逻辑。

根因证据链

 1. 崩溃前同一语句连续报错 4 次（全天仅 4 次，都在
  2.5 分钟内）：
 15:15:28 / 15:17:28 / 15:17:47 / 15:17:52  ERROR: invalid data for match in format string，STATEMENT: select to_char(current_date, 'YYYY年MM月DD日')，session 48，用户 
rdsAdmin，application_name=gsql。
 2. core 里出错处正在遍历一个 24 字节步长的格式项数组（add $0x18,%r13），当前元素 R13=0x7fed5d882648 的布局是 {kind=2, ptr=NULL}，即"标记为关键字节点、但节点指针为空"。
 3. 同一数组里正常元素的指针都指向 .data.rel.ro 的 DCH_keywords_Aformat 表，与本实例 sql_compatibility=A 
一致；说明该格式串在处理中文多字节字符（年月日）时被切分/查表失败，产出了一个残缺项。
 4. YYYY 已正常输出（out=0x7fed528a00b8 "2026"），崩溃发生在处理第 2 个元素（即紧跟 YYYY 的 年）时。

推断（未证实）：格式解析失败时留下了半初始化的解析结果（很可能是 to_char 的格式缓存项），后续复用该残缺项导致解引用 NULL。这能解释"先报几次 invalid data for match、再崩溃"的顺序。

临时缓解

把中文用双引号包成字面量，走标准 to_char 字面量路径（尚未验证）：

 select to_char(current_date, 'YYYY"年"MM"月"DD"日"');

或改为 to_char(current_date,'YYYY-MM-DD') 之后在应用层格式化，避开多字节格式串。这个畸形格式串很可能是 506 内核缺陷，建议带 core + ffic 日志提华为 case。

两次崩溃的 fault offset 完全一致：datetime_to_char_body + 0x1b0，si_code=1, si_addr=0xc（空指针 + 0xc 偏移）。按 fault line 判定为同一个 bug。

根因

to_char 的格式串解析结果被跨格式复用/污染，导致 DCH_to_char 遍历到 key == NULL 的格式节点后解引用崩溃。

崩溃指令（RIP=0x…79d0）：

 mov 0xc(%rax),%edx     ; rax = 0 → 读 key->id (offset 12)
 cmp $0xbc,%edx         ; → 188 项跳转表（DCH 关键字分派）
 movslq (%r15,%rax,4),%rax ; r15 = 跳转表基址

即 node->key 为 NULL，仍无条件读 key->id。

从 core 里把 FormatNode 数组打出来（ptype FormatNode = {int type; const KeyWord *key; char character; int suffix;}，stride 24）：

 [0] {type=0, key=0x0,                    ...}
 [1] {type=2, key=DCH_keywords_Aformat+2832}
 [2] {type=2, key=0x0, character='-'}   ← 崩溃点在这里
 [3] {type=2, key=DCH_keywords_before+384, character='-'}
 [4] {type=1, key=DCH_keywords_Aformat+504}

一个"已标记为关键字、但 key 为空"的半成品节点，前后还残留着 - 这类属于另一个格式串的节点 —— 说明这个节点数组不是当前语句解析出来的。

复现（在干净进程上做的对照实验，已跑通）

重启后进程内格式缓存为空：

 - select to_char(current_date,'YYYY年MM月DD日') → ERROR: invalid data for match in format string（每次都报）

同一进程内先用别的格式，再跑同一条语句：

 1. 'YYYY-MM-DD'      → 2026-11-15     ✓
 2. 'YYYY年MM月DD日'  → ERROR: invalid data for match in format string
 3. 'YYYY年MM月DD日'  → 2026-11-15     ✗ 错！用的是上一条语句的格式
 4. 'YYYY-MM-DD'      → 2026-11-15     ✓

第 3 行说明：一次失败的解析污染了缓存，后续相同语句会拿到别的格式的节点数组；某些缓存状态下拿到的节点数组里 key 为 NULL，就变成 SIGSEGV。

触发条件（已观测）

 - 语句：select to_char(current_date,'YYYY年MM月DD日')，sql_compatibility=A、lc_ctype=C
 - 格式串含中文多字节字符（年/月/日）→ 解析器在第一个非 ASCII 字节处匹配失败
 - 同一进程内之前执行过其他 to_char 格式串（生产环境就是被健康检查/其他 SQL 预热了缓存）
 - 崩溃前 gs_log 连续出现同一语句的 ERROR: invalid data for match in format string（15:15:28、15:17:28、15:17:47、15:17:52，全天仅这 4 次，且都是本语句），随后同一条语句下次执行即崩溃 
—— 这与"先报错、再复用坏缓存、再崩"的链条吻合

崩溃栈（core 与 ffic 日志两路互相印证）：

解决方案

  • 修复版本： GaussDB Kernel 506.0.0.spc0500
  • 规避方案：修改业务语句，在使用to_char/to_timestamp函数时，将第二个入参的中文字符用""包含起来，如替换为select to_char(current_date, 'YYYY"年"MM"月"DD"日"');

后续问题

其实当时在测试环境收集ffic日志时，我有发现在506.0.0.spc0100和506.0.0.spc0500都有to_char引起的coredump，但是堆栈不一样。使用复现用例在spc0100上产生的coredump堆栈，在spc0500上没有出现。

spc0500上的这个堆栈我当时没有复现出来，后面华为研发会议解释了原因：
这个问题有个前提条件，特定时机内存不足。

上面有说到，to_char里的格式，其实是有缓存的，而这个缓存结构，分为头和体，GaussDB在收到一种新格式时，会把这个格式写进缓存，先写头，然后再写体，假设写体的时候，申请内存不足了，体就会写入失败，但这个时候不会报错，而且没有把已写入的头还原（即没有保证原子性操作），客户端会话保持正常。再次调用到这个格式时，发现头有，就以为体也有，访问过去，其实是一块坏的内存，就coredump了。

cache_getnew 的关键代码（0x15331d0）：

 cmp $0x10,%eax          ; n = cache->n
 jle 0x15332a5           ; n<=16 → ent = cache->entries + n*0xca0
 0x15332b2: lea 0xc18(%rbx),%rdi     ; dest = ent->str   ← 你的崩溃就在这次拷贝
 0x15332b9: callq fill_DCH_cache_str ; → strncpy_s(dest,129,src,128)

0xca0=3232 是缓存项大小，0xc18 是项内 str 字段偏移，数组一共 17 项（0xd6a0）。

找到了真正的缺陷：缓存上下文先挂到 TLS、后分配节点数组

nls_date_fmt_cache_search 的惰性初始化（同一函数，0x14969b0）：

 0x1496aca  mov  %fs:(%r12),%r15              ; 保存当前内存控制器
 0x1496ad4  call alloc_zero(.., 0x10, ..)     ; 分配 DCHCacheContext(16B)
 0x1496af2  mov  %rax,%fs:0x36c0(%rbx)        ; ★ TLS 先发布 —— 源码 line 418
 0x1496afa  call alloc_zero(.., 0xd6a0, ..)   ; ★ 再分配 17 项节点数组 —— line 420
 0x1496aff  mov  %rax,(%r14)                  ; cache->entries = 数组 —— line 419

line 418 在 line 420 之前。所以只要第二个 54944 字节的分配抛错/返回空（内存不足、max_process_memory 到顶、内存控制器异常），TLS 里就留下一个 entries == NULL 
的"半成品缓存"，而且成功的那一半已经把 n=0、counter=0 写好了。

下一次任何 to_char(datea, 非热格式)：

 1. nls_date_fmt_cache_search：cache 非空、n==0 → 直接返回 NULL（不碰 entries，所以不崩）
 2. get_nls_date_format → cache_getnew：n=0 ≤ 16 → ent = NULL + 0 = NULL
 3. dest = NULL + 0xc18 = 0xc18 → strncpy_s(0xc18, 129, "...", 128) → 在 libc 里写 0xc18 崩掉

这与你给的栈完全吻合：cache_getnew → strcpy_s → libc，且崩溃地址会是 0xc18 附近（和你 119 上那几次 si_addr = 0xc 是同一类"空基址+小偏移"）。gdb 里 cache=0xc2b 
那种值是优化后参数回显不准，可忽略；决定性证据是 faulting 地址。

顺带说明 SPC0500 里日期类格式化共有 3 份缓存，都在 t_thrd.format_cxt：

 - fs:0x36b0 — timestamp/DCH 缓存（knl_thread_init 里主动建好）
 - fs:0x36b8 — 第二份（同上，entry 尺寸 0x6f90）
 - fs:0x36c0 — datea 缓存，knl_thread_init 只把它置 0（thread.cpp:166），真正的内容靠上面那段惰性初始化

只有 datea 这一份是"懒创建"的，所以只有它会踩到这个半初始化窗口。
