【GaussDB】会话里出现大量idle in transaction状态的问题排查

背景

客户DBA给应用开发人员宣讲GaussDB数据库的idle in transaction会话的监控告警后，开发人员自查，发现在开发环境中存在大量的idle in transaction会话，一时恐慌，于是来找DBA帮忙排查是不是应用代码哪里写得有问题。

数据库内核版本是 506.0 SPC0500 集中式。

检查应用

应用软件使用的spring框架接mybaitis，连接使用基于DBCP修改的连接池，提取pg_stat_activity里idle in transaction会话最后执行的SQL，找到应用代码中出现的位置，发现并没有声明事务。
在执行SQL的前后加上断点打印getautocommit的值，是 true。
当时有怀疑是连接池上做了反射导致autocommit是假的，因为该客户项目要求连接默认为非自动提交。但后续确认了连接池并没有做相关修改。
也怀疑了该SQL之前执行的其他任务有开启事务但没结束事务，由于应用代码比较复杂，而且是多线程的，不好排查。

抓包分析

指定客户端的端口进行网络抓包，得到客户端与数据库之间的所有交互内容。观察到在该查询SQL之前，的确有出现过start transaction的语句，但是有提交。服务端返回客户端会返回事务状态，很明显最后客户端查询SQL，服务端返回的事务状态是idle，但此时数据库中查询该会话的状态仍然是idle in transaction。

难道是数据库有问题？

检查数据库

仔细观察pg_stat_activity视图，发现这个idle in transaction的会话和以前遇到的长得不太一样，它的xact_start是空的！就是说它没有事务开始时间！
一个没有事务开始时间的会话，怎么可能是idle in transaction状态呢？而且此时它的pid是0。
隐隐感觉与GaussDB的线程池模式有关，当一个会话执行完任务闲置时，pid就会置为0。

手动在gsql中使用start transaction模拟开启一个事务,该会话状态为idle in transaction，xact_start不为空；然后执行commit，会话状态变为idle，xact_start变为空，一切正常。

核心发现

通过分析源码，xact_start 为空但 state 为 idle in transaction 的情况确实可能在线程池模式下发生，关键路径如下：

关键代码路径（commit_pending 场景）

在扩展查询协议（PBE）中，当 enable_beta_features = true 且事务没有分配事务ID（只读事务）时，存在一个特殊的优化路径：

exec_sync_message() 中：

if (u_sess->attr.attr_common.enable_beta_features && 
   GetTopTransactionIdIfAny() == InvalidTransactionId) {
   u_sess->xact_cxt.commit_pending = true;  // 延迟提交！
} else {
   finish_xact_command();  // 正常提交
}

PostgresMain() 主循环 中的处理顺序：

步骤1 (line 9302-9304): 先报告状态
   if (IsTransactionOrTransactionBlock()) {
       pgstat_report_activity(STATE_IDLEINTRANSACTION, NULL);  // 设置状态为 idle in transaction
   }

步骤2 (line 9345): 发送 ReadyForQuery 给客户端

步骤3 (line 9346-9348): 然后才提交事务（延迟提交）
   if (u_sess->xact_cxt.commit_pending) {
       finish_xact_command();  // → CommitTransaction() → pgstat_report_xact_timestamp(0) 清除 xact_start
   }

竞态窗口

在步骤1到步骤3之间，存在一个时间窗口：

  • state 已经被设置为 STATE_IDLEINTRANSACTION（步骤1）
  • xact_start 还没有被清除（步骤3还没执行）

在步骤3之后到下一次循环开始前：

  • state 仍然是 STATE_IDLEINTRANSACTION（未更新）
  • xact_start 已经被清除为 0

这就是 xact_start = NULL 但 state = idle in transaction 的状态。

线程池模式的特殊性

在线程池模式下，这个不一致性更容易被外部观察到：

  1. 会话分离（Detach）：线程池中的会话在空闲时可以被分离（DetachSessionFromThread），分离时 pgstat_couple_decouple_session 只更新 st_procpid 和 st_tid，不会修改 st_state 和 st_xact_start_timestamp

  2. 状态持久化：会话的 BEEntry 中的状态在分离后仍然保留，如果在上述竞态窗口期间或之后查询 pg_stat_activity，就能观察到这个不一致状态

  3. 正常流程不存在此问题：在非 commit_pending 路径中，finish_xact_command() 在 exec_sync_message() 中立即调用，事务在状态报告之前就已经提交，IsTransactionOrTransactionBlock() 返回 false，状态会被正确设置为 STATE_IDLE

总结

场景是否存在不一致
普通查询协议（Simple Query）否
扩展查询协议 + enable_beta_features = false否
扩展查询协议 + enable_beta_features = true + 只读事务是
上述场景 + 线程池模式是，且更容易被外部观察到

   private static long getSessionId(Connection conn) throws SQLException {

       ResultSet rs = stmt.executeQuery(
           "SELECT sessionid FROM pg_stat_activity WHERE pid = pg_backend_pid()");
       if (!rs.next()) throw new SQLException("无法获取 sessionid");

       rs.close();

       ResultSet rs = stmt.executeQuery("SHOW enable_thread_pool");
       boolean enabled = false;
       if (rs.next()) {
           enabled = "on".equalsIgnoreCase(rs.getString(1));
       }
       rs.close();
       stmt.close();
       return enabled;

代码已更新。核心修正：

之前的问题：用了 setAutoCommit(false)，JDBC 会发显式 BEGIN，事务块状态变成 TBLOCK_INPROGRESS。此时 CommitTransactionCommand() 只提交子命令不提交外层事务，xact_start 根本不会被清零。

  • firstchar=83（Sync）命中：72
  • line11743 命中：8
  • line12568 命中：36
  • 角色命中：role1=0, role2=80

条件概率：

  • P(line12568 | Sync) = 0.500
  • P(line11743 | Sync) = 0.111

6. 完整根因判定

-M pending 改变了后端执行上下文（线程角色与事务状态机门控状态），使得 Sync 阶段在 gs_process_command 内对 t_thrd.postgres_cxt.xact_started 所门控的事务收尾链命中模式不同：

  • 在 8000（-M pending）中，line12568 收尾链几乎不被命中，finish_xact_command() 不触发，表现为 idle in transaction
  • 在 5432（非 pending）中，line12568 收尾链被稳定命中并触发事务收尾，表现为 idle

这不是 JDBC 输入差异，而是服务端模式驱动的分支选择差异。

7. 结论摘要

本问题的决定性差异不在 JDBC 报文本身，而在服务端启动模式引起的事务收尾门控状态差异。

  • 8000（-M pending）偏向“不收尾”画像 -> idle in transaction
  • 5432（非 pending）偏向“收尾”画像 -> idle

8.1 会话上下文初始化详细路径（函数级）

下面给出“会话上下文初始化路径差异”的明确函数链。

  1. 公共主链（两端都经过）

  • postmaster_main

  • ThreadPoolControler::stay_in_attach_mode / ThreadPoolWorker::set|get_connect_node_mode

  • gauss_db_worker_thread_main<knl_thread_role=X>

  • backend_run

  • PostgresMain

  • gs_process_command

  1. 8000（-M pending）观察到的主路径画像

  • 线程角色混合：role2 主导，同时存在 role1 命中（Sync 聚焦采样：role1=16, role2=64）

  • 在 gs_process_command 中更偏向 line11743 画像，line12568 基本不命中

  • 在 +8246~+8269 门控点更常走“跳过 finish_xact_command”分支

  1. 5432（无 -M pending）观察到的主路径画像

  • 线程角色集中：role2 主导（Sync 聚焦采样：role1=0, role2=80）

  • 在 gs_process_command 中 line12568 命中显著升高

  • 在 +8246~+8269 门控点更常满足收尾条件并调用 finish_xact_command

  1. 关键分歧点（你问的“路径为何不同”）

  • 说明：路径A/路径B不是两条完全不同的“全链路函数序列”。
    差异主要发生在 backend_run 之前的 worker 角色与会话绑定/延续阶段；
    一旦进入 backend_run -> PostgresMain -> gs_process_command，后半段函数名是汇合且相同的。

  • 图中“worker attach/分配策略差异”的具体含义：
    在 -M pending 侧，调度更容易形成 role1+role2 混合分配；
    在非 pending 侧，调度更集中到 role2 主导分配。
    该角色分配差异是后续 line11743/line12568 命中分布差异的前置原因。

  • 分歧不在 SQL 文本，而在 postmaster_main 设置的模式状态被线程池调度路径读取后，
    进入了不同的 worker 会话绑定/延续路线（role 组合与上下文时序不同）

  • 该差异最终在 gs_process_command 的事务收尾门控点放大，体现为 xact_started 取值分布差异

总结

GaussDB这个state异常显示对数据库本身并没有什么影响，而且一般监控告警查未提交事务也是限定了事务开始时间超过一定范围的，xact_start为空的会话是不会触发告警的，所以几乎没什么影响。
但是通过本次故障诊断，发现了就算数据库版本、运行环境、数据库GUC参数、部署形态完全一致时，数据库对于同一任务的执行行为也可能会由于启动命令是否加 -M primary参数 发生差异，所以之后本地模拟复现问题的时候，还是得注意一下数据库的启动命令是否一致。
另外，让AI直接对GaussDB做gdb调试来定位复杂问题，看来也不是不行，只要能稳定复现问题场景。没源码的时候人工反编译断点定位找问题非常耗时间，但交给AI，效率极大提高了。
