【YashanDB】自治事务比ORACLE慢几百倍？查下来锅不在AT,在commit刷盘时机

2026-11-17 0 阅读

【YashanDB】自治事务存储过程比ORACLE慢几百倍？查下来锅不在AT,在commit刷盘时机

前言

做ORACLE向国产库迁移的适配评估，自治事务(autonomous transaction)是个绕不开的东西,ORACLE里写日志的经典套路就是游标循环里调一个带pragma autonomous_transaction的存储过程，逐条insert逐条commit,主事务该回滚回滚，日志照样留下来。这个模式在ORACLE上跑了几十年了，没人觉得它有什么性能问题，但是迁到YashanDB上会怎样呢？

我手上有台麒麟V10 SP3的虚拟机，里面docker跑着ORACLE 19c,外面装着YashanDB 23.4.7,同一台机器同一块盘，正好拿来做个对照。我本来只想测个性能，顺便看看sql%rowcount、sqlerrm、dbms_utility.format_error_backtrace这些在自治事务里的传递行为一不一致，结果我在性能这块测出来一个两百多倍的差距，然后顺着挖下去发现根因还挺有意思的，不是自治事务本身的锅，是commit刷盘时机的设计差异(这里藏着个ORACLE会丢失commit数据的问题)。行为那边也挖出两个迁移必改的真差异。

本文所有数字都是这台机器上实测的，脚本都贴出来了，有兴趣的同学可以自己复现，欢迎拍砖。

本文中出现的 "AT" 为 "autonomous_transaction"的缩写

先说结论

  • 游标循环里调存储过程做insert+commit,ORACLE 31µs/次,YashanDB 7080µs/次，差228倍;换成自治事务过程更是差到593倍
  • 自治事务机制本身不贵，空AT过程调用ORACLE只比普通调用多0.24µs,YashanDB多4µs,都是微秒级
  • 根因:YashanDB的commit没写在循环控制语句里时(经典写法的commit在过程体里,AT也一样)每次同步fsync,而ORACLE把log file sync推迟到最外层PL/SQL块结束再等，一个20000次commit的块只产生1次刷盘等待。这是ORACLE从v6就有的commit point optimization，代价是块执行中途crash会丢部分已提交事务,后面kill实例实测丢过108个已经返回成功的commit
  • 本机wslc容器复测(fsync均值2.2ms):差距缩到35倍上下,根因第二环境复现;远端AT/嵌套的附加代价没复现，那截推断收回
  • 行为语义基本一致:事务独立性、异常传播、sql%rowcount共享、OUT参数异常路径丢失，两边都一样
  • 两个真差异:format_error_backtrace的帧序相反;raise_application_error的错误号体系完全不兼容,ORACLE的-20000..-20999在YashanDB上全部非法

两边数据都在同一块盘上，我用df和lsblk确认过，都是sda上的klas-root,不存在"ORACLE的redo落在快盘上"这种干扰因素。机器8个vCPU,盘是虚拟盘，后面会看到这块盘的fsync延迟相当感人。

计时用dbms_utility.get_time(),这玩意一个tick是10ms不是1ns,别搞错了。每个场景预热一次然后测3轮取中位数，含insert的场景每轮前truncate,单会话，两库先后跑不并行。有个口径我要先交代:两边的迭代次数N不一样,ORACLE游标场景N=20000、嵌套N=50000,YashanDB游标和嵌套只有N=2000,为什么？因为YashanDB太慢了,按ORACLE的量跑要跑几个小时。。。us_per_call是归一化后的每次调用耗时，可以直接比，每轮计时都大于13个tick,量化误差控制在个位数百分比。

用例构造

源表2000行，日志表一张，存储过程一组，两边脚本完全同构:

drop table at_log;

场景7个:S1游标FOR循环调p_plain,S2游标FOR循环调p_at,S3数值循环调空AT,S4数值循环调空普通过程,S5三层嵌套p_l3→p_l2→p_l1叶子commit,S6三层嵌套叶子是AT,S7顶层AT包两层普通嵌套。游标场景的核心块长这样(YashanDB版,ORACLE版把循环套10遍):

declare
  t0 number; t1 number; n number;
  cursor c is select id from at_src;
begin
  for r in c loop p_at(r.id); end loop;
  for run in 1..3 loop
    execute immediate 'truncate table at_log';
    t0 := dbms_utility.get_time;
    for r in c loop p_at(r.id); end loop;
    t1 := dbms_utility.get_time;
    select count(*) into n from at_log;
    dbms_output.put_line('S2 run' || run || ' ticks=' || (t1-t0) || ' us_per_call=' || round((t1-t0)*10000/2000,2) || ' rows=' || n);
  end loop;
end;
/

慢在哪？排查过程

第一次跑崩了

其实一开始两边用的是同一份脚本同样的N,然后YashanDB跑了11分钟还没跑完S1的第一轮，我查了下at_log的行数才19912行，折合每次insert+commit要30ms。ORACLE那边同样的逻辑30µs就跑完了。这肯定不对劲，我直接把进程kill了重新设计探针。

拆分探针

把insert、commit、过程调用、游标这几个因素拆开，我各跑了2000次:

declare
  t0 number; t1 number;
  cursor c is select id from at_src;
begin
  t0 := dbms_utility.get_time;
  for r in c loop p_plain(r.id); end loop;
  t1 := dbms_utility.get_time;
  dbms_output.put_line('Q1 cursor_loop_2000_p_plain ticks=' || (t1-t0));
  t0 := dbms_utility.get_time;
  for i in 1..2000 loop p_plain(i); end loop;
  t1 := dbms_utility.get_time;
  dbms_output.put_line('Q4 numeric_loop_2000_p_plain ticks=' || (t1-t0));
  t0 := dbms_utility.get_time;
  for i in 1..2000 loop insert into at_log values (i, 'x'); commit; end loop;
  t1 := dbms_utility.get_time;
  dbms_output.put_line('Q5 numeric_loop_2000_inline_ins_commit ticks=' || (t1-t0));
end;
/

输出:

Q1 cursor_loop_2000_p_plain ticks=1629
Q4 numeric_loop_2000_p_plain ticks=1703
Q5 numeric_loop_2000_inline_ins_commit ticks=7

也就是说游标不是问题，数值循环一样慢，但是inline写insert+commit只要70ms跑完2000次,35µs一次，和ORACLE一个量级。差异锁定在commit语句的写法位置上:写在循环体里，还是写在任何循环之外的过程体里。我再补一组探针确认:

Q6 2000_proc_insert_no_commit_plus_1 ticks=20
Q7 2000_inline_insert_proc_commit ticks=1419
Q8 2000_numeric_loop_p_at ticks=1338

Q6是调过程insert但不commit,2000次加末尾1次commit,200ms,正常;Q7是inline insert然后调一个只有commit的过程,14.2秒,7.1ms一次;Q8是数值循环调AT过程,13.4秒。
简单来说就是:YashanDB里commit走不走同步刷盘,看它写没写在循环控制语句里，而不是看它在不在被调用的过程里。经典写法的commit在过程体里、不在任何循环中，所以每次吃默认同步路径;顶层inline commit恰好写在循环体里,走批量。AT也一样道理:看commit写在哪，不看单元是不是自治。这条规则的官方文档出处和实测边界，下一小节说。

官方文档怎么说

后来我去翻了YashanDB官方文档,23.4.7的PL语句页里有独立一句:"在PL循环控制语句中COMMIT等同于COMMIT WRITE BATCH NOWAIT。"COMMIT语法页补语义:单独COMMIT默认WRITE WAIT IMMEDIATE,就是等刷盘;NOWAIT直接返回,"此时不保证redo日志成功写入磁盘";BATCH是攒redo一起刷。所以批量路径是官方承认的，条件写的是"在循环控制语句中"。

但是我实测的边界比文档字面窄，在本机(fsync 2.2ms环境)补了几个探针:

探针形态折合每次路径
L2过程内2000次循环insert+commit,调1次20µsbatch
L3顶层循环内嵌套块里commit ×200045µsbatch
L5过程包for 1..1循环commit,调2000次1385µssync
L7过程内for 1..2循环commit,调1000次1290µs/调用1 sync+1 batch
L9外循环1000 ×内循环1..1 commit1270µssync

规则是:每轮循环执行的第一个commit仍走同步刷盘，第2次迭代起才BATCH NOWAIT,与调用层级无关(L2在被调过程里照样快),与块嵌套无关(L3);单迭代循环永远不触发,外层循环的回跳救不了内层首迭代(L9)。拿远端Q5的70ms交叉验证:1次同步(约8ms)加1999×31µs,对得上。文档把等价关系写成无条件一句,没提首迭代这个边界;实现是不是在回跳边才置循环标记，没做源码级证实。

盘到底有多慢

7.1ms这个数字很像fsync延迟，我用自带的fio量了一下(4k write,fsync=1,8秒):

fsync mean_us= 8426.932381454 p50= 6127.616 p99= 52166.656
write mean_us= 8.70689989500000001

纯write只要8.7µs,一加fsync就是8.4ms,p99更是52ms。虚拟盘嘛，正常。7.1ms和8.4ms同量级，对上了,YashanDB过程内commit就是被这块盘的fsync钉死的。

ORACLE凭什么这么快

同一块盘,ORACLE的commit也要刷redo啊，凭什么31µs？我查了下v$system_event:

EVENT                   TOTAL_WAITS    SEC    US_PER_WAIT
log file sync           34             .71    20880.6

容器刚起不久，前面已经跑了十几万次commit了,log file sync居然只 waits了34次，单次均值20.9ms——和盘的fsync延迟又是一个量级。所以ORACLE不是每次commit都等刷盘。我做了个对照实验，一个匿名块里游标循环调过程commit两万次，前后各查一次等待计数:

alter session set container=pdb1;
select total_waits as before_waits from v$system_event where event='log file sync';
declare
  cursor c is select id from split_test.at_src;
begin
  for pass in 1..10 loop
    for r in c loop split_test.p_plain(r.id); end loop;
  end loop;
end;
/
select total_waits as after_waits from v$system_event where event='log file sync';

BEFORE_WAITS
	  34
AFTER_WAITS
	 35

20000次commit,1次log file sync。实锤了:ORACLE把commit的redo刷盘等待推迟到最外层PL/SQL块结束,而且这个推迟穿透过程调用边界，也穿透AT边界(S2的数据可以佐证)。块内随便commit,反正redo先攒着,块退出时一把等完。

这玩意有个官方名字,叫commit point optimization，ORACLE从version 6就有了。

《Oracle Database Transactions and Locking Revealed》2nd ed. (Apress, 2021)，Ch.5 Transactions，小节 "COMMITS in a Nondistributed PL/SQL Block"（纸页 p.130 起），第一句就是：

"Since PL/SQL was first introduced in version 6 of Oracle, it has been transparently using an asynchronous commit."

AskTom上Connor McDonald答过两个专问AT日志场景的帖子(一个,另一个),一个帖子里他当场跑了50万次AT调用,每个块log file sync只+1;另一个说得更直白:"In PLSQL (autonomous transaction or otherwise) we can 'cheat' a little because the only time you get control back is at the conclusion of the call",演示末尾还专门补了句"You'll see the same result if you comment in the pragma above"——把AT的pragma注释打开结果一样，AT没有特殊化。Tom Kyte早在2009年的说法是"every time you commit, you wait for log file sync (outside of plsql anyway)"。他和Darl Kuhn合著的Oracle Database Transactions and Locking Revealed里"COMMITS in a Nondistributed PL/SQL Block"一节讲了理由:PL/SQL被当成批处理程序，调用方在整个块跑完之前不知道结果,所以块内commit等价于commit write NOWAIT,只在返回客户端前等一次redo落盘。注意书里把这种情况和COMMIT WRITE NOWAIT一起列在Durability一节,明说committed不等于持久化了，块跑到一半实例crash的话,redo还没被LGWR写盘的那部分已提交事务会丢，这是写在明面上的取舍,不是bug。Jonathan Lewis的Oracle Core第6章有个小节标题就叫"ACID Anomaly",flashdba2013年用SLOB量过:6400次user commits,redo synch writes只有97次。

我回头又补了几组对照,这回不看等待事件,看redo synch writes计数器(它统计同步刷盘请求,比log file sync稳,因为19c的_use_adaptive_log_file_sync默认TRUE,走polling模式时不记等待事件):

W0_baseline                            user_commits=0     redo_synch_writes=0     lfs_waits=0
W1_after_20000_proc_commits            user_commits=20000 redo_synch_writes=0     lfs_waits=0
W2_after_20000_AT_commits              user_commits=40000 redo_synch_writes=0     lfs_waits=0
W3_after_2000_inline_commit_write_wait user_commits=42000 redo_synch_writes=2000  lfs_waits=2000
W4_after_2000_inline_plain_commit      user_commits=44000 redo_synch_writes=2000  lfs_waits=2000

四个负载在同一个匿名块里跑。20000次过程commit和20000次AT commit都是零同步刷盘,和Connor的演示对上。换成显式的commit write immediate wait立马就是2000次同步,redo synch time 925个厘秒,折合每次等待4.6ms,又被我们这块盘钉回去了,所以这个优化用显式WAIT就能破，只是正常没人这么写。顶层对照也有意思:同一会话2000条顶层autocommit的insert,redo synch writes也是2000,一比一,说明推迟只在PL/SQL块内生效。块退出那一次推迟的sync也抓到了,新会话里20000次commit,redo synch writes=1,log file sync=1。

还有个例外,块里要是走了dblink(分布式事务),优化就失效,退回逐次commit等待,因为两个库都指着这个commit的持久性,没法偷懒,书里是这么解释的,flashdba也实测过(加loopback dblink后redo synch writes从97涨到6564)。

所以换个角度看,YashanDB这种循环外commit的逐次fsync其实是"老实"写法，每次commit都真持久化了，只是这个老实在慢盘上太贵;它循环内的批量路径官方同样是NOWAIT,不保证逐次持久化，见前面文档那节。ORACLE的快是有前提的,前提就是牺牲块中持久性,迁移的时候别光顾着骂YashanDB慢。

所以根因就清楚了，不是YashanDB的AT实现得烂，是两家的commit刷盘策略不同:ORACLE是plsql块级延迟，过程内commit被摊薄到31µs;YashanDB过程内commit逐次fsync,被盘延迟钉在7ms。盘越慢差距越大，这是个结构性差异。没准换块fsync一百微秒的NVMe差距能缩到几倍~十几倍，但只要这个策略差异在，游标循环逐条commit的写法在YashanDB上就永远比ORACLE吃亏。

至于远端YashanDB为什么嵌套三层(S5)比直调(S1)贵一倍、AT(S2)比普通过程贵2.6倍，当时我推断是每多穿一层调用边界/AT边界就多一次刷盘，7ms的整数倍。这个推断后来没站住，火焰图负载和本机复测两套数据都没复现附加代价，复测那节细说，抬高成因未定论。

块跑到一半把实例kill了会怎样

前面说ORACLE拿块中持久性换速度，书里也明说了，但是"会丢部分已提交事务"这句话到底有多真，我决定直接试:一个匿名块里循环insert+commit一百万次，跑到第20秒的时候pkill -9把ORACLE所有进程连LGWR一起干掉，等价实例crash,然后重启走crash recovery，数还剩多少行。杀之前commit到哪了得有个不走redo的证据，我让过程每次commit返回后用UTL_FILE往OS文件写一行id，容器死了宿主OS还活着，这文件就是"kill前已commit成功"的铁证。A臂用默认commit,B臂把commit换成commit write immediate wait(就是前面W3那个破优化的写法)，同样杀法同样时机。

臂实测速度杀前最后commit的id恢复后幸存丢失
A 默认73µs/次274969274861≥108
B 显式WAIT3.5ms/次573957400

A臂那108行，commit调用在kill前已经成功返回了，恢复之后查不到，因为commit record杀的时候还在log buffer里没落盘,recovery把它们当未提交事务处理了。丢的也只是尾巴:最多一个LGWR刷盘周期内的commit，我poll了v$sysstat的redo writes,大概104次一秒，折合周期9.6ms，108个commit按14.5k/s算就是7.4ms，对得上，前面二十多万行都活得好好的。只杀会话的server进程不算数,LGWR还活着，秒级就把log buffer刷下去了,丢的场景是实例crash或者掉电这一类。

B臂零丢，但是3.5ms一次，比A臂慢48倍,这就是每次等盘的价钱。所以ORACLE默认那个选择翻译过来就是:拿极端场景下几百行的尾巴，换48倍吞吐。YashanDB那边我没做同款测试，不推断它丢不丢，但是它循环外commit每次真落盘这点，前面7ms和fio的8.4ms已经对上了;循环内路径官方是NOWAIT,丢不丢同样没测。

换台机器再测,差距跟着fsync走

前面所有数字都出自那台麒麟VM,慢盘是差距的放大器，这个说法靠不靠谱得换套环境验证。我本机Windows的wslc里跑着两个容器，Oracle还是19c那个镜像，YashanDB是23.4.7.100，远端是.113，小版本不一样先记着;提交参数和PL编译选项核对过，和远端一致。同一套脚本同样的N原样搬过来，串行跑。我本来以为本机NVMe盘fsync怎么也得百微秒级，结果fio一量不是那么回事:纯write确实快，27.8µs,但是4k write加fsync=1均值2.19ms,p50 2.15ms，p99 3.0ms。WSL2的容器盘是vhdx套NTFS再套NVMe，flush一次还是要两毫秒，比远端8.4ms好4倍，离裸盘还差一个数量级。所以"换快盘差距就消失"这个预期一开始就不成立，能验证的只是差距跟不跟着fsync延迟走。

先交代口径:本机Oracle三轮抖动比远端大，S1三轮25/37.5/49.5µs，WSL2调度加上宿主是我日常用的机器，不是静默实验室，中位数能看单轮别信;S2那个54倍是Oracle中位数偏低(25µs)抬出来的,看S1/S5/S6/S7的31~35倍更稳。

然后看机制复现没有。YashanDB过程内commit 1.3ms，贴着fio的2.2ms;拆分探针也复现:顶层块inline insert+commit 2000次40ms,折合20µs一次，同样的insert+commit写进被调过程就是1340µs一次，同库内差67倍。Oracle那边20000次过程内commit，redo synch writes和log file sync都只+1，块级延迟刷盘换个环境照样在。根因不是那台VM的偶然现象，是两家commit路径的结构性差异，第二环境复现了。

差距幅度也对上了:fsync从8.4ms到2.2ms快约4倍，S1倍数从228到35缩约6.5倍，YashanDB绝对值7080µs到1315µs缩5.4倍，Oracle基本不动(31µs到37.5µs，在抖动范围内)。YashanDB的成本跟着刷盘延迟走，Oracle的成本近似常数，两边数据都支持这条曲线。照这个趋势外推，真换fsync百微秒的裸NVMe差距应该进个位数~十几倍，这个是外推不是实测，先记在这。

但是有个意外。远端S2比S1贵2.6倍、S5比S1贵2.2倍，我前面推断是每穿一层调用边界/AT边界多一次刷盘。本机这套数据里S2/S1=1.03,S5/S1=0.99,凡是有commit的场景全在1.3ms上下，AT和嵌套一点附加代价都没有。加上远端火焰图那轮p_at负载实测7.4ms≈S1而不是S2，这个推断已经有两个独立反证,我收回。远端那个抬高到底是.113和.100的版本差异还是当时盘的状态，没隔离验证，不下结论，有兴趣的同学可以继续挖。

行为一致性对比

性能之外我把传递行为也测了一遍，用例和两边输出挑重点贴。

sql%rowcount是会话级共享的

外层update 5行，然后调AT过程(里面insert+commit),前后各读一次sql%rowcount;再测AT内部第一条DML之前读到的rowcount:

declare
  rc1 number; rc2 number;
begin
  update at_src set pad = 'x' where id <= 5;
  rc1 := sql%rowcount;
  p_at(9201);
  rc2 := sql%rowcount;
  dbms_output.put_line('[B3] rc_before_at=' || rc1 || ' rc_after_at=' || rc2);
  rollback;
end;
/

ORACLE输出[B3] rc_before_at=5 rc_after_at=0,YashanDB一模一样。AT内部读到的也是外层的7(B4用例，外层update 7行后调AT,AT里先读rowcount再insert),两边都是7。

可以发现sql%rowcount在两边都是会话级共享的,AT能继承外层的值,AT里的SQL也会覆盖外层的值。B3/B5里那个0不是"AT把rowcount清零了",是AT末尾那条commit把rowcount变成0了，这个细节迁移的时候容易误判。游标循环里也一样，调完AT后sql%rowcount=0,cursor%rowcount正常递增1..5,两边一致。

事务独立性和异常传播

外层insert不commit,调AT insert+commit,然后外层rollback,数行数:两边都剩1行,AT提交的留下来了。AT里insert之后raise,外层捕获,AT里那条insert自动回滚，两边可见行数都是1(只剩外层自己的未提交insert)。AT看不见外层未提交的行，两边都是0。这些核心语义完全一致，没得挑。

AT异常退出时OUT参数会丢

这个两边也一致,但是是个容易踩的坑:

create or replace procedure p_at_capture(out_msg out varchar2, out_bt out varchar2) as
pragma autonomous_transaction;
begin
  insert into at_log values (9401, 'cap');
  raise_application_error(-20003, 'CAP_BOOM');
exception when others then
  out_msg := sqlerrm;
  out_bt := dbms_utility.format_error_backtrace;
  raise;
end;
/

想着在AT的handler里把sqlerrm和backtrace塞进OUT参数带出来，然后raise给外层，结果外层收到的两个OUT参数都是空的,ORACLE和YashanDB都空。AT正常返回时OUT参数正常带回(B10对照用例验证过)。也就是说异常路径下OUT参数不回传，想从AT里带诊断信息出来不能走这条路。

两个真差异

raise_application_error的错误号体系不兼容

上面那个-20003在ORACLE上是标准用法,-20000..-20999是ORACLE留给用户的自定义错误号区间。但是在YashanDB上跑,sqlerrm出来的是这个:

YAS-06805 error number argument to raise_application_error of -20003 is out of range

官方文档有说范围为 30000~99999 。
https://doc.yashandb.com/yashandb/23.5/zh/All-Manuals/Development-Guide/PL-Reference-Manual/Built-in-Advanced-PL-Packages/DBMS_STANDARD.html

其实之前我就有文章说过这个问题。

YashanDB只收正数，映射成YAS-n,负数全军覆没,ORACLE那套-20xxx的惯例在这边一个都用不了。这意味着迁移的时候所有raise_application_error都要改号，更要命的是捕获端按错误号关联的自定义异常(exception e_custom; pragma exception_init(e_custom, -20001))和按sqlcode分支的逻辑全部失效。本次行为测试第一轮在YashanDB上实际传播的就是这个YAS-06805本身，换成50001/50002/50003重测之后，异常传播、自动回滚的语义和ORACLE是一致的。

backtrace帧序相反

两层嵌套raise,外层捕获后打format_error_backtrace,帧内容和行号两边完全一致(脚本同构所以行号也对得上),就是前缀不同,ORACLE是ORA-06512,YashanDB是YAS-04015,匿名块属主ORACLE不显示名字,YashanDB显示个空引号""。这些是外观差异，无所谓。

但是B8那个AT里handler重抛的场景，帧序反了。ORACLE:

ORA-06512: at "SPLIT_TEST.P_AT_CAPTURE", line 9
ORA-06512: at "SPLIT_TEST.P_AT_CAPTURE", line 5
ORA-06512: at line 4

YashanDB:

YAS-04015 at "SYS.P_AT_CAPTURE", line 5
YAS-04015 at "SYS.P_AT_CAPTURE", line 9
YAS-04015 at "", line 4

line 5是原始raise_application_error,line 9是handler里的raise。ORACLE最近的帧在前(栈顶往下),YashanDB原始raise在前。普通调用链(B6/B7)两边都是从叶子往外层排，看不出区别，只有重抛这种同一过程出现两帧的场景才暴露。解析backtrace做错误归因的迁移代码要注意这个，别按帧序取"第一帧"当出错点。

总结

  • 自治事务本身两边都便宜，迁移不用怕AT这个机制;怕的是"游标循环/深层嵌套里调过程逐条commit"这个ORACLE经典写法，在YashanDB上会被循环外commit的同步fsync钉死，本次慢盘环境实测228~593倍
  • 远端AT/嵌套的附加代价(2.2~2.6倍)在火焰图负载和本机.100复测里都没复现，成因未定论，迁移评估别拿它当依据
  • 缓解方向:把commit挪进顶层多迭代循环里(官方BATCH NOWAIT,但逐次不再保证持久化),或者攒多行一次commit减少次数，或者换低fsync延迟的盘。给过程体包一层1..1循环没用，实测照样同步;包成2迭代循环每次调用也仍付1次同步。有没有参数能让循环外commit走批量路径，我翻了下COMMIT_WAIT/COMMIT_LOGGING已经是WAIT/IMMEDIATE默认了，没找到别的开关，这个就抛给感兴趣的人去试试了。另外，GaussDB的自治事务也由于commit刷盘时机对性能有很大影响，所以之前我有篇文章介绍一些改造手段来提效，在YashanDB中也可参考（https://www.darkathena.top/archives/Optimizing-Autonomous-Transaction-Logging-in-GaussDB-Stored-Procedures-A-Comprehensive-Test-and-Evaluation）
  • 行为语义(事务独立、异常传播回滚、sql%rowcount共享、OUT参数异常丢失)两边一致，迁移风险集中在两处:raise_application_error错误号必须重映射,backtrace帧序解析逻辑要改
  • 口径提醒:单会话、慢盘VM、ORACLE是INTERPRETED编译，倍数不是绝对值，换硬件会收窄，但commit刷盘策略的结构性差异还在;本机wslc复测实测35倍上下，收窄幅度和fsync延迟对上了，裸NVMe个位数倍是外推没实测
  • 别只看快慢:ORACLE块内commit是异步的，块跑完之前crash会丢部分"已提交"事务(官方书里明说的ACID取舍,kill实例实测丢的是最后一个LGWR刷盘周期里的尾巴,本次108个已返回成功的commit);YashanDB循环外commit逐次fsync慢但每次真落盘，可它循环内inline路径官方也是BATCH NOWAIT,同样不保证逐次持久化,crash丢不丢没测。对日志可靠性要求极高的场景，先看清自己的commit写在哪条路径上，再反过来评估这个差异

注:本文的测试执行和初稿整理是交给AI(Qoder)干的，所有数字均为上述环境实测，脚本可复现，其中如有疏漏，请联系本人改正。完整的7场景脚本、9个行为用例和原始输出都在at_bench目录，篇幅有限就不全部贴出来了，欢迎大家来讨论或拍砖。
